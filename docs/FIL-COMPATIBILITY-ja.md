# V9968 KANJI表示のエミュレータ間比較 — 2026-11-23

今回の中央付近の区切り線は、検証に使用したV9968拡張openMSXと、
vimSXが対象とするV9968のFILレジスタ仕様が一致していないために発生します。
「openMSXは高解像度の描画が苦手」という説明では不正確でした。
この結果は、使用したカスタムビルドについてのものであり、すべてのopenMSXに
共通する不具合という意味ではありません。

| 比較対象 | FIL指定 |
|---|---|
| vimSX VI9IN / VI9EX | R#20 bit 5（R#20=21h） |
| 手元のV9968 RTL `vdp_cpu_interface.v` | R#20 bit 5を `ff_flat_interlace_mode` に設定 |
| BlueMSX+参照ソース `VDP.c` | `vdpIsFlatInterlace` がR#20 bit 5を参照 |
| 使用したopenMSXのソース `VDP.hh` | `isFIL()` がR#21 bit 6を参照 |

使用したopenMSX実行ファイルのSHA-256は以下です。対応するローカル
ソースツリーのビルド出力と、検証用runtimeへの配置ファイルは同一です。

`6b8e83483b7bfa70f7eff85a853fd521dfeb02a72508140c906c199237f5acaf`

## 動作による切り分け

VI9IN・VI9EXそれぞれを別の検証用ディスクで起動し、同じ画面について
次の比較を行いました。COM、エミュレータ、ROMのファイルは変更していません。
デバッガによるレジスタ変更は、この診断用プロセス内だけで行いました。

1. vimSXが設定したR#20=21h、R#21=00hの画面を保存。
2. R#20を01hに変更。FIL指定を外しても、画面は1とピクセル単位で完全一致。
3. R#20を21hへ戻し、旧指定のR#21=40hを設定。表示と区切り線の位置が変化。
4. R#21を00hに戻す。画面は1とピクセル単位で完全一致。

内蔵・外付けとも同じ結果です。R#20の値はレジスタに保存されますが、
このopenMSXのFIL表示判定には使われていません。
旧指定を与えた画面は診断結果であり、互換修正や合格画面としては扱いません。

BlueMSX+の現行COMによる実画面確認、および5タイプの編集・保存試験は
`validation-kanji80.json` に記録しています。通常版・従来版の漢字モードは
標準インターレースを使用し、このFIL指定不一致とは別です。

## 修正版の検証（2026-11-23）

HRAのRTLコミット `453d5f32b0cad874e7b9d4f885fae5f183afe024` を基準に、
openMSXの新V9968プロファイルをR#20 bit5のFIL、R#20 bit6のCEIEへ修正しました。
FIL時はR#9のEO指定に依存せず両フィールドを合成します。
CEI保留は割り込み許可と分離し、実際のコマンド完了で設定、port+4で解除します。
状態保存・復元でも保留状態と割り込み出力を保持します。

修正版SHA-256:
`d91238bbc38cf8302a4ce68b8e83ccab28ea1f32260cb5f5572464e322c8cc17`

内蔵・外付けでFILのレジスタ切り替えと復元、漢字表示、編集・保存、
DOS復帰、277,980バイトの文書保持、全16バンクのCPU入出力を検証しました。
Geo3D従来/拡張形式の線・面・テクスチャ描画も検証しています。
エディタを旧FIL仕様へ合わせる変更はしていません。実機検証は未実施です。

通常版の先頭文字欠けは別原因です。`FIRST-CELL-FIX-ja.md` を参照してください。
